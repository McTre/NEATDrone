# NEATDrone — Master Plan

## 1. Concept

NEATDrone is a top-down twin-stick shooter built around evolving enemy robots. The player moves through an automated facility while hostile robots are controlled by NEAT (NeuroEvolution of Augmenting Topologies).

The central idea is not simply that enemies become stronger. The robots gradually learn how to use the information and abilities available to them, while a separate facility-level **Master AI** observes what is causing its robots to fail and introduces new hardware capabilities.

The player is never given an exact description of what the enemy has learned. Changes are discovered through robot behavior and through comments made by the Master AI over the facility loudspeakers.

The intended experience is a feedback loop:

**Player develops tactics → robots fail → Master AI adapts hardware → NEAT learns to use it → player discovers new weaknesses and deception tactics.**

---

## 2. Core Design Principles

### 2.1 Master AI and NEAT are separate systems

This separation is fundamental.

**Master AI / Director**
- Does not control individual robots.
- Observes combat telemetry and robot failures.
- Chooses hardware/sensor/ability upgrades.
- Adds new inputs and outputs that NEAT robots may use.
- Communicates with the player through facility speakers.

**NEAT**
- Controls individual robot behavior.
- Evolves through generations/waves.
- Receives only the sensory inputs currently available to the robot hardware.
- Learns how to use newly unlocked inputs and outputs without being told their correct purpose.

The Master AI provides tools. NEAT discovers how to use them.

---

## 3. Enemy Perception

Robots should never receive unnecessary ground-truth information about the world.

For example, a robot should not receive:

`object_is_grenade = true`

Instead, it receives descriptions generated by its available sensors.

Possible sensory families:

- Basic environmental/wall sensing
- Vision
- Night vision
- Thermal vision
- Audio
- Advanced audio classification
- Object recognition
- Motion sensing

Sensors can have multiple upgrade levels.

### Example: audio progression

**Basic audio**
- sound detected
- strength

**Directional microphone**
- sound direction
- strength

**Advanced microphone**
- direction
- strength
- approximate sound-category values

Possible deliberately non-semantic sound categories:

- KLANG
- SHIII
- PLÄTS
- ZHUUU
- KOPKOP

The categories describe perceived sound characteristics, not their meaning.

A grenade and a thrown piece of metal may therefore initially appear very similar to a robot.

---

## 4. Deception as a Core Mechanic

Imperfect perception is intentional.

The player should be able to exploit correlations learned by the robots. For example:

1. Grenades repeatedly kill robots.
2. Robots learn that small thrown objects producing a KLANG-like sound are dangerous.
3. The player throws harmless metal debris.
4. Robots may evade it because their learned model generalizes incorrectly.

Later sensor upgrades may allow NEAT to distinguish the objects more accurately, forcing the player to develop another deception.

The desired relationship is two-way learning:

- NEAT learns patterns in the player's behavior.
- The player learns patterns in NEAT's behavior.
- The player can intentionally provide misleading evidence.

---

## 5. Lightweight Object Signatures

The simulation must remain practical to author.

Interactive objects should have only a small AI signature, preferably around 3–5 manually authored properties. Physical information already known by the game engine should be derived automatically.

Example object metadata:

```text
size = SMALL
material = METAL
temperature = WARM
impact_sound = KLANG
```

The engine already supplies values such as:

- position
- velocity
- movement direction
- collision events

Sensors translate this shared object information into observations. Objects should not contain separate data for every possible sensor.

Possible coarse shared categories:

**Size**
- tiny
- small
- medium
- large

**Material**
- soft
- hard
- metal
- organic

**Heat**
- cold
- warm
- hot

**Sound**
- KLANG
- SHIII
- PLÄTS
- ZHUUU
- KOPKOP

The deliberately low information resolution encourages generalization and mistakes.

---

## 6. Master AI / Director

The Master AI does not need to be a machine-learning model.

It can be a deterministic Director that accumulates upgrade scores from meaningful robot failures and player successes.

The game should prefer concrete events over abstract labels such as `PLAYER_USES_MINES`.

Example:

```text
EVENT: ROBOT_KILLED_BY_MINE

Object Detection +6
Thermal Vision   +2
Mobility         +1
```

Another example:

```text
EVENT: ROBOT_KILLED_IN_DARKNESS

Night Vision    +6
Thermal Vision  +3
Better Hearing  +1
```

This means upgrades emerge primarily from tactics that are actually effective against the robots.

### Upgrade selection

At the end of an appropriate wave/level:

1. Update all upgrade scores from accumulated telemetry.
2. Determine which next-level upgrades have reached their unlock thresholds.
3. If several upgrades are ready, choose the eligible upgrade with the strongest score/priority.
4. Unlock only the selected upgrade.
5. Preserve progress toward the remaining upgrades.
6. Play another wave/level and evaluate again.

The exact scoring model can be tuned later.

---

## 7. Upgrade Families and Levels

Many upgrades belong to persistent families rather than being one-off abilities.

Examples:

### Object Detection
- Lv0: no dedicated object perception
- Lv1: detects nearby floor objects
- Lv2: gains additional size/movement information
- Lv3: gains coarse material classification
- Lv4: improved feature resolution

### Audio
- Lv0: no useful hearing
- Lv1: sound strength
- Lv2: direction + strength
- Lv3: KLANG / SHIII / PLÄTS / ZHUUU / KOPKOP categories
- Lv4: improved classification/directional accuracy

### Vision
- basic vision
- improved vision
- night vision
- improved night vision

### Thermal
- heat detection
- heat direction/area
- improved thermal resolution

### Mobility
- normal movement
- dash
- improved dash
- possible additional movement capability

### Defense
- basic body
- shield
- improved shield behavior/recharge

Not every level needs to add neurons. Some upgrades can simply improve the accuracy or range of an existing sensor.

---

## 8. Master AI Personality and Communication

The facility Master AI is the primary antagonist and communicates through loudspeakers.

Its dialogue should expose adaptation indirectly rather than presenting upgrade notifications.

Example after repeated use of darkness:

> "I've noticed your preference for turning off the lights. Fortunately, I have a solution."

The player can infer that some form of low-light perception may have been introduced but is not told its exact implementation.

The Master AI should ideally sound observant, analytical, and increasingly familiar with the player's habits rather than simply threatening the player.

Its dialogue can be triggered from real telemetry and actual upgrade decisions.

---

## 9. NEAT Evolution

Each enemy is controlled by a NEAT genome/network.

Generations are evaluated through combat performance. Exact fitness design will require experimentation and should avoid rewarding only direct damage, because that could produce simplistic suicidal rushing behavior.

Potential fitness components include:

- survival time
- useful movement
- approaching a commanded/search area
- damage dealt to player
- successful contact with player
- avoiding projectiles
- avoiding hazards
- useful positioning
- reduced time stuck against walls

Champion genomes should survive between generations so useful behavior is not unnecessarily lost.

Future versions may support several evolutionary lineages/species with naturally emerging behavioral differences.

---

## 10. Long-Term Player/AI Relationship

The long-term goal is for different players to shape different enemy populations.

Examples:

- Heavy darkness use encourages better low-light sensing.
- Successful mines encourage object detection and/or thermal sensing.
- Long-range kills encourage countermeasures relevant to ranged combat.
- Repeated melee kills encourage close-range responses.
- Repeated sound distractions encourage improved audio perception.

Because the Master AI changes the available hardware while NEAT independently learns behavior, an upgrade should not instantly solve the player's tactic. The first generation receiving a new sensor may use it badly. Later generations may discover effective strategies.

This delay is desirable and should remain visible in gameplay.

---

## 11. Development Philosophy

Build the smallest possible learning experiment first.

Do not implement the full sensor ecosystem, facility campaign, dialogue system, or adaptive Director before basic NEAT movement has been proven.

Development order should be roughly:

1. Basic arena and player combat.
2. NEAT-controlled movement.
3. Learning to respond to a Master AI target-area signal.
4. Learning to avoid walls rather than using hard-coded avoidance.
5. Add player vision input.
6. Verify pursuit behavior evolves.
7. Add projectile perception.
8. Verify projectile avoidance can evolve.
9. Test melee-related behavior.
10. Only then begin building the full Master AI upgrade system and richer sensors.

The first prototype exists to answer one question:

**Can this evolutionary architecture produce visibly interesting combat behavior?**

## 10. Environmental Perception and Occlusion

The world must control what information is physically available to robot sensors.

A sensor upgrade should never bypass the environment by directly exposing ground-truth player coordinates unless that is explicitly the intended sensor capability.

### Darkness

Areas of the facility can be dark. Basic visual perception fails or becomes severely limited in darkness.

Robot destruction telemetry should preserve relevant environmental context, for example:

```text
EVENT: ROBOT_DESTROYED
cause = PROJECTILE
player_was_in_darkness = true
```

This concrete event can later contribute to multiple upgrade families:

```text
Night Vision   +6
Thermal Vision +3
Better Hearing +1
```

The Master AI therefore learns from **what successfully caused robot failure**, rather than from an abstract label such as "player likes darkness."

### Occlusion

Walls, machinery and other opaque obstacles must block visual sensing.

Vision is a sensor result derived from the real world state and line of sight. NEAT should not receive player information through opaque geometry.

This allows tactics such as:

- breaking line of sight
- hiding behind machinery
- moving through dark areas
- firing from concealment

### Sound

Sound is represented as lightweight world events rather than a full acoustic simulation.

A sound event can contain a small payload such as:

```text
position
strength
category
```

Robots receive only the subset their current microphone hardware can perceive.

Player gunshots should create sound independently of the projectile. Areas of the environment can also create sounds when crossed or interacted with.

Examples include metal flooring, debris, machinery, water or other noisy surfaces.

This makes hearing useful but inherently ambiguous: a robot may hear a location without knowing whether the sound was a gunshot, a thrown object, a footstep, or environmental noise unless later hardware provides enough descriptive inputs.

---

## 11. Upgrade Inputs and Outputs

Hardware upgrades change the **action and observation space** available to NEAT.

The Master AI never supplies the behavioral solution.

Examples:

```text
Night Vision upgrade
→ visual information becomes available in darkness

Directional Microphone upgrade
→ new sound_direction_x / sound_direction_y inputs

Sound Classification upgrade
→ KLANG / SHIII / PLATS / ZHUUU / KOPKOP inputs

Dash upgrade
→ new dash output

Shield upgrade
→ new shield output
```

NEAT must evolve the relationship between those inputs and outputs itself.

This rule is central to the architecture:

**Master AI changes what robots can sense or do. NEAT decides how robots behave.**

## 12. Perception Signatures, Sampling and Deception

World objects should expose a small set of normalized descriptive properties rather than semantic AI labels. Where practical, sensor-facing qualities use values in the `0.0–1.0` range. Content creation should rely on reusable profiles with optional overrides instead of requiring large hand-authored data sets for every object.

Examples include heat, visual prominence, movement, flash and sound-profile components. Sound classification should preferably use several independent feature values rather than one enumerated number, so an observation can partially resemble several sound qualities at once.

Robots must never receive hidden truth such as `is_grenade`, `is_decoy`, `is_player` or `weapon_type` unless a deliberately unlocked system explicitly provides such information. A robot may eventually behave as if it recognizes a shotgun, grenade or player because evolution has learned correlations between observable signatures and consequences.

### Sensor sampling

Sensors have a configurable sampling/update rate. They do not need to observe the world continuously every simulation frame. Better hardware can increase sampling rate, precision, classification quality or the ability to separate overlapping signals.

This creates a natural basis for sensor-confusion tools. A device may emit several rapidly changing sound, heat, visual or electronic signatures. A slow or low-quality sensor may perceive an ambiguous mixture while improved hardware can potentially resolve the signals more accurately.

### Decoys

Decoys are not special AI objects. They are ordinary world objects that intentionally generate believable sensor signatures.

Possible tools include:

- audio emitters
- heat emitters
- human silhouettes or projected images
- moving visual decoys
- combined multispectral decoys
- chaff/noise devices producing rapidly changing or overlapping signatures

A decoy therefore succeeds only because the robot's available sensors and evolved policy interpret its observations incorrectly.

A visual-only robot might evolve the correlation:

```text
human-like shape + movement
→ relevant threat

human-like shape + stationary
→ usually ignore
```

If this emerged because stationary human-shaped objects were normally decoys, the same policy may cause the robot to ignore the real player when the player stands completely still. This is **desired emergent behavior, not an AI bug**.

A later thermal sensor may provide enough additional information for evolution to distinguish the cases, but the upgrade itself must not provide the answer. NEAT still has to discover how the new input is useful. The player may later counter this with a heated decoy, restarting the adaptation cycle.

### Design rule: imperfect generalization is gameplay

Do not automatically correct an evolved misconception when it follows fairly from the information available to the robot.

Examples worth preserving include robots that:

- fear harmless thrown objects because thrown objects were usually explosives
- ignore a stationary player because stationary human-like observations were usually decoys
- overreact to a particular sound signature
- mistake a decoy for the player
- learn an overly specific response to a weapon signature

The player should be able to discover these misconceptions through observation and deliberately exploit them. A major part of the game is learning **what this particular evolved population currently believes about the world**.

## 13. Facility Intelligence and Robot Data Link

The Master AI controls and observes parts of a damaged facility. Its knowledge is explicitly limited by functioning infrastructure. Some rooms may have cameras, motion sensors, powered electronic doors and reliable maps, while damaged or unpowered areas may provide partial or no information.

The Master AI is scripted. It does not share NEAT's perception or policy. Facility events such as an electronic door opening, a camera sighting or a motion sensor activation can update the Master AI's knowledge independently of robot sensors.

The amount and freshness of facility information that can be transferred to NEAT robots should form its own upgrade family. Early robots may receive only a coarse alert area. Later upgrades may provide room-level map awareness, known exits, door states, recent facility events or route guidance. Even at high levels, robots receive only information the Master AI actually possesses.

Damaged maps, dead sensors, unpowered doors and unknown passages should remain meaningful. Player hacking can interfere with this information chain by disabling sensors, changing door states, cutting links or potentially creating misleading facility events.

This preserves the architectural separation:

```text
FACILITY / PLAYER ACTIONS
        ↓
SCRIPTED MASTER AI
        ↓
limited map / event / tactical data
        ↓
NEAT ROBOT INPUTS
        ↓
evolved behavior
```

The facility data link can become increasingly powerful without ever telling NEAT *what to do* with the information.

## Diegetic Progression and Hidden Numbers

Progression should remain grounded in the fiction of the facility. Avoid abstract player-facing upgrades such as `+5 HP`, `+10% damage`, or `+8% movement speed`.

Upgrades should instead represent concrete equipment, materials, software, sensors, or modifications that plausibly explain their effect. For example, increased protection could come from composite armor or ceramic inserts; greater carrying capacity from a harness or backpack; stealth improvements from sound-damping equipment or thermal masking.

Internal numeric values may still exist for simulation and balancing, but most should remain hidden. The player should learn capabilities through equipment descriptions, physical behavior, sound, visuals, Master AI dialogue, and experience.

The same rule applies to robots. The Master AI does not grant abstract stat bonuses to NEAT. It grants hardware, sensors, facility information, or physical capabilities. These expose new NEAT inputs/outputs or improve the quality and sampling rate of existing sensor data.

### Master AI Dialogue as a Diegetic Interface

At the beginning of a new level or sector, the Master AI may comment over the facility speakers on what it believes it learned from previous encounters.

The dialogue serves as narrative characterization, an intentionally incomplete hint about what the Master AI observed, and a diegetic indication that the next robot generation or facility behavior may have changed.

The Master AI should not announce technical unlocks such as `Night Vision Lv2`.

> "You seem much more comfortable in the dark than my drones. I found that discrepancy unnecessary."

It may also comment on measured emergent NEAT behavior:

> "They appear to have developed an aversion to your projectiles. Sensible."

Imperfect or strange NEAT behavior can be acknowledged by the Master AI and become part of the fiction rather than something the game must hide.

### The Master AI Is Not Omniscient

Master AI knowledge and dialogue must respect the information actually available from the facility.

```text
REAL WORLD
    |
FACILITY SENSORS
    |
MASTER AI KNOWLEDGE
    |
FACILITY / TACTICAL DATA LINK
    |
NEAT ROBOT INPUTS
    |
ROBOT BEHAVIOR
```

If a robot disappears in an unmonitored damaged sector, the Master AI may know only that contact was lost. It must not magically know how the robot was destroyed.

> "I lost six units in the maintenance sector. I don't know what you did there."

If functioning facility sensors observed the action, the Master AI may refer to it explicitly. Dialogue can therefore reveal useful information about surveillance coverage. Players can deliberately exploit blind areas, disable or hack sensors, or feed misleading information into the facility.

### End-of-Run Reveal

During a run, adaptation information remains intentionally incomplete. When the player dies, the run report may reveal substantially more:

- what the Master AI observed or inferred;
- which concrete upgrades it installed;
- which facility-information capabilities became available;
- measured NEAT behaviors and their effectiveness;
- behaviors that apparently emerged;
- behaviors that remained unreliable or failed to emerge.

Descriptions of NEAT learning should be based on measured behavior rather than claims about what the neural network "understands".

The report is also a learning tool for the player. A new run resets player-specific adaptation, but robots may start from a shared pretrained navigation baseline. The player retains knowledge about how their behavior shaped the previous opposition and can deliberately play more diversely or deceptively next time.

### Pretrained Navigation and Encounter Size

Basic wall navigation and response to an alert-area signal may be evolved before release and included as the robots' factory baseline. Players should not need to wait for fundamental locomotion to emerge during each run. This baseline does not include player-specific tactics or the use of later sensor upgrades.

Start with roughly 6–8 active enemies per encounter. The size of an offline training population is independent of the number of robots facing the player. New sensors and counter-tactics still require learning during the run; their acquisition speed must be measured separately from the benefit of pretrained movement.
